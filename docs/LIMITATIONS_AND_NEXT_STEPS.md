# Known Limitations and Next Steps

This document separates limitations directly visible in the supplied source from recommended engineering work.

## 1. AI and analytics limitations

### Directly visible in source
- The anomaly detector is trained/scored on the same batch in `fit_predict`; the evaluation script also scores the same synthetic data used to fit it.
- Synthetic labels are generated by fixed timing rules and are not real-world ground truth.
- The 88th-percentile threshold flags high-ranked events by design; it is not calibrated to a clinical false-alarm target.
- `PatternClassifier.confidence` is a formula, not a calibrated probability.
- The composite risk score uses hand-coded weights and cutoffs.
- The next-dose predictor's `base_adherence` is an event-frequency proxy, despite a docstring referring to on-time adherence.
- Day/time factors compare event counts, not dose-level adherence.
- The next-dose predictor accepts `patient_id` but does not filter events by it and stores prediction history under patient ID 1.
- The cognitive engine also reads all events and schedules without applying its `patient_id` argument.
- The feature extractor maps only the first encountered schedule per compartment.
- No serialized model, labeled real dataset, or training history is included in the supplied archive.
- `ml_core.py` imports NumPy, but `requirements.txt` does not declare NumPy. The supplied Raspberry Pi environment had NumPy installed, but a clean installation from this requirements file alone may not satisfy the AI modules.
- `database/database.py:init_database()` runs only `schema.sql`; it does not automatically run `schema_extensions.sql`, although API routes and prediction history refer to tables created by that extension file.

### Recommended improvements
1. Match each opening event to the correct medication schedule and dose window.
2. Represent missed doses explicitly using scheduled-dose records, not only compartment openings.
3. Separate event frequency from dose adherence.
4. Make all analytics queries patient-scoped.
5. Add NumPy to the declared dependency list (with a Raspberry Pi-compatible installation instruction/version policy).
6. Add an explicit, versioned migration step for `schema_extensions.sql` and test a clean database initialization.
5. Use a time-based or person-based train/validation/test split.
6. Calibrate the anomaly threshold on validation data.
7. Track precision, recall, F1, false alerts per day, and missed events on a held-out real test set.
8. Add unit tests for timezones, midnight boundaries, multiple daily schedules, empty datasets, and repeated timestamps.
9. Persist evaluation metadata and human-reviewed labels.
10. Add a baseline rule-based model for comparison.

## 2. Hardware and system limitations

- A lid opening does not prove medication ingestion.
- The single load cell is assigned to compartment 4 only.
- A weight change threshold of 5g may be unsuitable for small pills or noisy mechanical mounting; it requires empirical calibration.
- The RTC manager returns a datetime marked UTC; verify that the RTC is set and interpreted consistently.
- The current API source does not show authentication or role-based access control.
- The source has patient-specific endpoints and medical-profile fields; protect these before network exposure.
- The application binds to all interfaces (`0.0.0.0`) on port 5000.
- The startup banner prints a fixed IP address rather than discovering the current network address.

## 3. Testing limitations

The smoke-test file covers database initialization, seeded compartments, and basic Flask endpoints. The repository also contains hardware test scripts named `test_*.py`.

A generic `pytest` run may collect hardware scripts as tests and fail on a machine without Raspberry Pi GPIO libraries. In the review environment, test collection stopped because `gpiozero`, `lgpio`, and Flask were not installed there. This does not prove the same tests fail on the Raspberry Pi, where the project dependencies were previously installed.

A cleaner structure would move manual hardware scripts under a directory not auto-collected by pytest (or rename them) and use explicit test paths, mocks, and fixtures.

## 4. Safety and privacy

- AI outputs must be labeled as experimental monitoring signals.
- Do not change dosage, medication type, or schedule based solely on an AI score.
- A caregiver or qualified clinician should review any concerning signal.
- Add authentication, authorization, encrypted transport, secure backups, and data-retention controls before real patient use.
- Keep the database, exported logs, and credentials out of public source control.
